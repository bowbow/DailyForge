# Domain model

## Overview

The domain centers on daily assignments, immutable progress events,
completions, and historical Wall of Goodness entries.

```text
ChallengeDefinition
        │ selected for a user and local date
        ▼
DailyAssignment ──────── ProgressEvent*
        │ completion policy satisfied
        ▼
Completion ───────────── StreakState
        │
        ▼
GoodnessEntry
```

## Current runnable slice

The in-memory development adapter implements four deterministic tracking
policies while preserving the broader model below:

- `counter`: positive, idempotent increments toward a visible target.
- `checklist`: each known item can be completed once.
- `confirmation`: one durable self-attestation for a concrete action.
- `timer`: positive duration increments toward a visible target.

The development adapter creates one assignment per category. Each completion
transaction derives a human-readable result and snapshots the challenge into
one private wall entry. The day-based streak advances on the first completion
for a local date; additional completions that day still increase lifetime and
category totals. A proposal may be replaced or skipped before acceptance
without a streak penalty. Narrative accounts, artifact attachments, reopened
checklist items, durable persistence, and cross-device reconciliation remain
future extensions.

## Core entities

### User

Relevant domain attributes:

- Stable user ID.
- IANA time zone.
- Challenge-category preferences.
- Physical limitations and excluded movements.
- Available equipment.
- Training-day intensity or preference when supplied.
- Reminder preference.

Sensitive onboarding data should be minimal and must not become part of logs or
challenge analytics.

### ChallengeDefinition

A reusable, versioned challenge template:

- ID and version.
- Category.
- Title and instructions.
- Optional practiced qualities.
- Tracking mode.
- Completion policy.
- Expected effort or duration.
- Difficulty.
- Safety notes and contraindication tags.
- Consent or privacy note where relevant.
- Eligibility rules.
- Lifecycle status: draft, active, retired.
- Optional Creativity program context: program version, goal IDs, challenge
  lane, primary and supporting Studio Habits, Studio Structure, reflection
  prompt, and related active-work ID.

Editing a definition creates a new version for historical integrity.

### CreativeWork

A user-controlled creative project context:

- Stable ID.
- Title and artistic inquiry.
- Status: active, paused, or finished.
- Last-updated timestamp.

Changing CreativeWork status is independent of daily challenge completion and
streak state. The transition is deliberately reversible so a user can resume a
paused or previously finished work without penalty. Challenge definitions may
reference a work, but completing a challenge does not silently finish it.

### DailyAssignment

The challenge offered to one user for one local date:

- Assignment ID.
- User ID.
- Local date and time zone used for assignment.
- Challenge definition ID and version.
- Status.
- Presented title, instructions, and completion-policy snapshot.
- Proposed, accepted, replaced, skipped, expired, and completed timestamps as
  applicable.
- Replacement lineage.

At most one active assignment should exist for a user, local date, and category.

### ProgressEvent

An immutable, idempotent record of progress:

- Event ID generated by the client or server.
- Assignment ID and user ID.
- Event kind.
- Numeric value, duration, checklist item, narrative, or artifact reference as
  appropriate.
- Occurred-at time and received-at time.
- Device-generated sequence metadata if needed for reconciliation.

Event kinds include:

- CountAdded.
- DurationAdded.
- ChecklistItemCompleted.
- ChecklistItemReopened.
- AccountRecorded.
- ReflectionRecorded.
- ArtifactAttached.
- ArtifactRemoved.

Corrections should be represented by explicit compensating events or a clearly
audited edit model rather than silently rewriting synchronized history.

### CompletionPolicy

Examples:

- CounterAtLeast target.
- DurationAtLeast target.
- AllRequiredChecklistItems.
- NonEmptyAccount.
- ManualAttestation, used sparingly and explicitly.

The policy is visible to the user before acceptance. Completion evaluation must
be deterministic and shared between client preview and server authority.

### Completion

Created once per assignment:

- Completion ID.
- Assignment ID and user ID.
- Completion timestamp.
- Local completion date and time zone.
- Policy and derived result.
- Optional reflection.

Completion commands are idempotent. The same assignment cannot produce multiple
streak increments or wall entries.

### GoodnessEntry

A private historical snapshot:

- Entry ID.
- Completion ID.
- User ID.
- Completion local date.
- Category and practiced qualities.
- Challenge title and prompt snapshot.
- User's completion account or summarized measurable result.
- Optional reflection.
- Optional artifact references.
- Optional Creativity program context snapshot.
- Created and edited timestamps.
- Highlight marker.

The entry can be edited or deleted by the user without corrupting the completion
and streak ledger. Product behavior for deleting a wall entry versus deleting
the underlying completion must be made explicit before implementation.

### StreakState

Derived or transactionally maintained:

- Current streak.
- Longest streak.
- Last completed local date.
- Lifetime completion count.
- Category counts.

## Important invariants

1. A user has at most one active daily assignment per local date and category.
2. A progress-event ID is processed at most once.
3. Progress belongs to exactly one assignment and its owner.
4. A completed assignment cannot be completed again.
5. A completion creates at most one wall entry. The daily streak advances at
   most once per local date, while each distinct completion contributes to
   lifetime and category totals.
6. Challenge-definition edits never rewrite historical assignments or wall
   entries.
7. A skipped or expired assignment does not count as complete.
8. Replacing a challenge stays within its category and cannot leave two
   simultaneously active assignments for that category.
9. Server authorization is checked by ownership, not merely by knowing an ID.
10. Time-zone changes cannot award two completions for the same intended day.
11. Changing active creative-work status cannot create a completion, wall entry,
    or streak change.

## Local-day and time-zone policy

- Store instants in UTC.
- Store IANA time-zone identifiers, not fixed numeric offsets.
- Snapshot the assignment time zone for that assignment's lifecycle.
- Define a local day from that snapshot for streak purposes.
- Treat time-zone travel and date-line transitions as explicit edge cases in
  tests.

The exact policy for changing time zone during an accepted challenge remains an
implementation decision and requires tests before release.

## Challenge selection

Initial selection may be curated and deterministic. It should consider:

- Recent categories and challenges to avoid repetition.
- User exclusions and physical constraints.
- Training-day intensity if known.
- Expected available time.
- Whether an external volunteer opportunity is still valid.

Selection must explain why a challenge is ineligible but need not expose a
complex scoring system. Personalization must not infer medical or moral traits.

## Example flow

```text
Definition:
  "Accumulate 20 push-ups today"
  policy = CounterAtLeast(20)

Assignment:
  offered for 2026-11-03 in America/Los_Angeles

Events:
  08:20 CountAdded(5)
  13:10 CountAdded(7)
  18:30 CountAdded(8)

Derived progress:
  20 / 20

Completion transaction:
  assignment completed
  streak advanced
  wall snapshot created
```
